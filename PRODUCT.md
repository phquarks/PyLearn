# Product

<!-- impeccable:product-schema 1 -->

## Platform

adaptive

## Users

Confirmed primary user: **school and university students** learning Python for
coursework — exams, assignments, and competitions. Their motivation is largely
external (a grade, a deadline, a contest), which makes visible progress and
comparison against peers load-bearing rather than decorative.

The product's own intake screens offer four stated goals (work, study,
curiosity, career change) and three experience levels (beginner, knows the
basics, confident). Those remain available to every user; students are the
audience that settles contested decisions.

## Product Purpose

Teach Python fundamentals through short, gamified exercise sessions instead of
lecture-style theory. The stated promise on first run is "Python in 5 minutes a
day." Success is a learner who returns daily, keeps a streak alive, and reaches
a working program of their own.

## Positioning

**Undecided — do not invent one.** Asked directly what a neighboring app could
not truthfully copy, the answer was "not yet determined." Three candidates were
on the table and none was chosen: practice on real code (assembling lines,
finding bugs) rather than recall; five-minute microsessions as the core promise;
or a finite route to a first real program instead of an endless lesson feed.

Until this is settled, design must not assert a differentiator in copy or
structure. Record it here when decided.

## Operating Context

Phone in hand, short sessions fitted into a day that belongs to something else.
The learner moves along a lesson path, spends hearts on mistakes, earns XP, and
is ranked weekly against other learners in a league.

## Capabilities and Constraints

**Implementation today.** React 19 + TypeScript + Vite, styled with a single
`src/styles/global.css` and Tailwind v4 available via the Vite plugin. Supabase
provides email/password auth and stores progress in one table,
`learning_profiles`, guarded by row-level security. Nearly all screen code lives
in one reducer-driven file, `src/App.tsx`.

The platform above is `adaptive`: the target is a native app on both iOS and
Android. The current web build is a prototype standing in for it, which is why
screens render inside a phone-shaped frame (`PhoneShell`). Native design rules
govern decisions, not web habit.

**Content.** Five lessons — Variables, print(), if/else, Loops, Lists — with
four exercise types: multiple choice, fill-in-the-blank, assembling a line from
code blocks, and finding the bug. Four exercises per lesson.

**Gamification.** XP, day streak, and hearts. A weekly league with standings.

**Screens.** onboarding, auth, goal, experience, language, home, lesson, result,
progress, league, profile.

**Frozen for the current design work.** Data and logic must not change: no
schema edits, no new persistence, no new queries. The auth screen and the
four-slide first-run onboarding are explicitly out of scope and must be left
as they are.

**Two new screens** — snake customization and an accessories shop — are
presentation only. Static data, no purchases, no writes to the database.

**Known gaps that must not be dressed up as working.** League standings are
invented placeholder names. The language picker lists six languages but only
Python is active; the rest are marked as coming later. An unused scaffold from
an abandoned portfolio-app idea still sits in `src/` (router, eight screens, a
zustand store, project/profile types) and is imported by nothing.

## Product Principles

1. **Progress must be visible and comparable.** The audience is externally
   motivated; streaks, XP, and standings are the product's spine, not ornament.
2. **Short beats deep.** A session must stay completable in the promised five
   minutes. Anything that lengthens the core loop needs justification.
3. **Practice over terminology.** The exercise types exist to make learners read,
   assemble, and repair code rather than recall definitions.
4. **Never dress a placeholder as real.** Invented standings, inactive languages,
   and non-functional shop items must read as what they are.
5. **The settled flow stays settled.** Auth and first-run onboarding change only
   on an explicit request.

## Accessibility & Inclusion

No product-specific requirement or standard has been established yet. Native
platform baselines apply by default — minimum touch target sizes, respect for
system text scaling, and sufficient contrast — and should be confirmed rather
than assumed if a formal target matters.
